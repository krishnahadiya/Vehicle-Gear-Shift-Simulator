# Vehicle Gear Shift Simulator

A manual-gearbox driving simulator. The **C engine** (compiled to WebAssembly) does all vehicle calculations; the **HTML/CSS/vanilla JS** frontend only sends inputs (pedals, gear, ignition) and draws the results. No JavaScript libraries, no Node.js, no Python.

```
Vehicle-Gear-Shift-Simulator/
├── frontend/
│   ├── index.html      Home screen + dashboard markup
│   ├── style.css       Dark dashboard theme, responsive layout
│   ├── script.js       UI only: gauges, gear lever, pedals, history, calls into C
│   ├── sim.js / sim.wasm   Generated by Emscripten (do not edit)
│   └── assets/
├── backend/
│   ├── vehicle.h/.c        Vehicle presets, drag/rolling/grade forces, motion integration
│   ├── engine.h/.c         Torque curve, friction, idle governor, fuel flow, heat model
│   ├── transmission.h/.c   Gear ratios, clutch bite curve, shift validation, wear
│   ├── simulation.h/.c     Session: pedals, clutch slip, stalling, warnings, score, history, files
│   ├── main.c              Emscripten API for JS  +  native self-test (25 checks)
│   ├── Makefile, build.bat, test.bat
└── README.md
```

## 1. Architecture

```
 keyboard / touch / mouse
          │
      script.js  ── api_set_inputs(throttle, brake, clutch), api_set_gear(g), api_ignition(on)
          │          api_update(dt)            (once per animation frame)
          ▼
   sim.wasm  (C)  ◄─ simulation.c ─ engine.c ─ transmission.c ─ vehicle.c
          │
          └──► api_get(field) → speed, rpm, gear, fuel, temperature, score, warnings …
               api_history_* → event log, api_report() → text/CSV report
```

Each frame, `sim_update()` limits pedal speed, then runs the physics in 4 ms sub-steps for stability:

1. **Clutch**: torque = `max_torque × engagement(pedal) × tanh(slip / k)`. Engagement follows a smoothstep "bite" curve, so slipping, launching and stalling emerge naturally.
2. **Engine**: `I·dω/dt = throttle × torque_curve(rpm) − friction + idle_governor − clutch_torque`.
3. **Vehicle**: `m·a = clutch_torque × ratio × efficiency / r − brake − rolling − air drag − m·g·sin(slope)`.
4. **Post-frame**: stall detection, overheating, warnings, shift hints, jerk (smoothness), fuel use, score, history.

### Simplified physics (state these in your viva)
- Straight-line motion only; no tyre slip, weight transfer or suspension.
- Drivetrain is rigid apart from the clutch; no gearbox synchroniser model.
- Torque curve is a 9-point table, not a measured dyno curve.
- Fuel = indicated work ÷ 30% efficiency ÷ 32 MJ/L, with fuel cut on closed-throttle engine braking.
- Engine temperature is a lumped model (one heat capacity, thermostat + fan). Heating is faster than real life so overheating can be demonstrated in seconds.
- Gear wear, clutch wear and the score weights are teaching values, not engineering data.

### Driving modes
| Mode | Behaviour |
|---|---|
| Learner | Slow clutch return, lower stall speed, stronger idle, shift-up/down hints |
| Eco | Score weights fuel use most (target 6 L/100 km) |
| Sport | +15% power, quick clutch, relaxed fuel target |
| Hill | C generates rolling terrain from distance; gradient slider locked |

### Shift rules enforced in C (`transmission_validate_shift`)
- Clutch must be pressed (> 80%) with the engine running, otherwise **gear grind** (shift refused, gearbox wear).
- Reverse refused above 0.8 m/s; forward gear refused while rolling backwards.
- Downshift that would exceed redline is allowed but flagged **over-rev** (wear, no score).
- Neutral can always be selected.

### Score (0 to 100)
`shifting` (shift rpm in the sweet spot, no grinds) + `smoothness` (mean jerk) + `fuel use` (L/100 km vs mode target), weighted per mode, minus penalties for stalls, overheating, redline and lugging.

## 2. Build and run on Windows

### A. Test the C engine alone (Phase 2)
Needs `gcc` (MinGW-w64 or MSYS2).
```
cd Vehicle-Gear-Shift-Simulator\backend
test.bat
```
You should see `25 checks, 0 failed`. It also writes `session_report.txt` and `best_score.dat` (file handling demo).

### B. Install Emscripten (once)
```
git clone https://github.com/emscripten-core/emsdk.git C:\emsdk
cd C:\emsdk
emsdk install latest
emsdk activate latest
emsdk_env.bat
```
(Python is bundled inside emsdk as a build-tool dependency; your project code contains none.)

### C. Compile the backend to WebAssembly
In the same terminal (after `emsdk_env.bat`):
```
cd Vehicle-Gear-Shift-Simulator\backend
build.bat
```
This produces `frontend\sim.js` and `frontend\sim.wasm`. The equivalent command is:
```
emcc vehicle.c engine.c transmission.c simulation.c main.c -O2 -sMODULARIZE=1 -sEXPORT_NAME=createSimModule -sALLOW_MEMORY_GROWTH=1 -sEXPORTED_RUNTIME_METHODS=cwrap,ccall,UTF8ToString -sNO_EXIT_RUNTIME=1 -o ..\frontend\sim.js
```

### D. Serve and open
Browsers refuse to load `.wasm` from `file://`, so use a local web server. Emscripten includes one:
```
cd ..\frontend
emrun --no_browser --port 8080 .
```
Open **http://localhost:8080/index.html**. (Any static server such as VS Code Live Server also works.)

### How JavaScript calls C
```js
const M = await createSimModule();                       // loads sim.wasm
const update = M.cwrap('api_update', null, ['number']);  // void api_update(double dt)
const get    = M.cwrap('api_get', 'number', ['number']); // double api_get(int field)
update(0.016);                                           // C advances the physics
const rpm = get(1);                                      // F_RPM
```
Functions marked `EMSCRIPTEN_KEEPALIVE` in `main.c` are the only things exposed.

### Server-side alternative (not needed)
If a server were required, the same `simulation.c` could be wrapped in a C CGI program (read inputs from `QUERY_STRING`/stdin, print JSON). WebAssembly was chosen because it needs no server and keeps the demo offline.

## 3. Controls
| Key | Action |
|---|---|
| W / Up | Accelerator (builds up while held) |
| S / Down | Brake |
| Shift or A | Clutch (presses fast, releases slowly; or drag the clutch pedal) |
| R, N, 1 to 5 | Gear (or click the lever slots) |
| E | Ignition |
| P | Pause |

On touch screens drag the pedal bars up; each pedal works at the same time.

## 4. Feature test checklist
1. **Start**: choose vehicle and mode, press Start simulation. Press Start engine: rpm settles near idle.
2. **Interlock**: select 1st, stop engine, try to start without clutch → refused.
3. **Launch**: hold clutch, select 1, add ~30% throttle, release the clutch slowly. Car moves.
4. **Stall**: stop, select 3, release clutch quickly with no throttle (Eco mode) → "Engine stalled".
5. **Grind**: release clutch, then press a gear key → grind warning, gearbox condition drops.
6. **Reverse while moving**: drive, clutch in, press R → refused.
7. **Redline / over-rev**: hold 1st at full throttle; or downshift 5 to 1 at speed.
8. **Overheat**: Sport Coupe, neutral, hold W for about 25 s → temperature warning and shutdown at 120 °C.
9. **Hills**: drag the gradient slider to +10% and pull away; try −8% in neutral. Hill mode drives the slope automatically.
10. **Fuel**: lift off in gear above ~1300 rpm and watch "Fuel now" fall to 0 (fuel cut).
11. **History and report**: click Download report.
12. **Pause / Reset / Home**: buttons or P.

## 5. Demonstration plan (5 minutes)
1. Show the architecture diagram, then run `test.bat` to prove the C engine works without any frontend.
2. Learner mode: launch and shift 1→5 following the hints; point out rpm drop after each shift.
3. Cause a stall and a grind on purpose; show the history log and the falling transmission condition.
4. Switch to Hill mode and explain gradient force.
5. Download the report and show the file-handling code (`sim_report`, `sim_save_report`).

## 6. C concepts used (for the Advanced C subject)
| Concept | Where |
|---|---|
| `struct`, nested structs | `Vehicle`, `Engine`, `Transmission`, `Simulation`, `SessionStats` |
| `enum` | `Gear`, `ShiftResult`, `DriveMode`, `SimStatus`, `SimField` |
| Arrays and tables | torque curve, gear ratios, `MODES[]`, `WARNINGS[]`, vehicle presets |
| Pointers and dynamic memory | `sim_create` / `sim_destroy` (`calloc`/`free`), heap ring buffer for history |
| Modular design | one module per file with a header; `main.c` only wires things together |
| Bit flags | warning mask (`WARN_*`) |
| Variadic functions | `history_add(fmt, ...)` using `vsnprintf` |
| File handling | `sim_save_report`, `sim_load_best_score`, `sim_save_best_score` |
| Error handling | status enums, NULL and range checks, bounded `snprintf` |
| Conditional compilation | `#ifdef __EMSCRIPTEN__` in `main.c` |

## 7. Notes
- `fopen` inside WebAssembly writes to a virtual in-memory file system that is cleared on reload. The browser "Download report" button uses `api_report()` instead.
- Tuning values (masses, torque curves, ratios) live in `vehicle.c`; scoring weights in `MODES[]` in `simulation.c`.
